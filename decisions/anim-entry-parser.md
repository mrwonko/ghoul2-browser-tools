summary: src/animationCfg.ts groups commonTokenizer's token stream into anim-entry records — syntax only, no engine/runtime semantics; IncompleteAnimEntry is a distinct Kind rather than a bolted-on warning; no synthetic terminal marker; hand-rolled integer/number parsing; fields store the raw token, not a derived value; every entry carries every token (including skipped separators) it consumed.

`src/animationCfg.ts`'s `parseAnimationCfg(source)` is layered directly on `src/commonTokenizer.ts`'s `tokenize()` (#29) to group the flat token stream into `animation.cfg`'s `anim-entry` records (`reference/animation_cfg_grammar.abnf` lines 89-97). Several choices here are non-obvious enough to record, so `animevents.cfg`'s future parser and any consumer of `AnimEntry` don't silently contradict them.

## Syntax only: no engine/runtime semantics

`AnimEntry`'s fields are exactly what the grammar's `anim-entry` rule describes — five raw tokens, plus how they parse as `integer`/`number`. Deliberately out of scope: looking `name` up against the engine's built-in animation-name table, the `fps == 0 → 1` runtime default, and the `frameLerp` (`ceil`/`floor(1000/fps)`) computation the engine derives from `fps` at load time. None of that is part of the file format itself — it's downstream interpretation a caller (or a later story) layers on top of "here is the record's 5 raw tokens and how they numerically parse."

## `IncompleteAnimEntry` is a distinct `Kind`, not a warning bolted onto `AnimEntry`

`commonTokenizer.ts` already established both patterns: `QuotedToken` stays one `Kind` regardless of termination (an unterminated quote is still structurally "a quoted token", flagged via a warning), but `Eof` is its own `Kind` because its shape is genuinely different (a `reason`, not token content). A record that runs out of real tokens partway through is the `Eof` case, not the `QuotedToken` case — it's missing 1-4 *required* fields, not just anomalous in an otherwise-normal shape. Splitting `AnimEntryKind.IncompleteAnimEntry` out gives the common path (`AnimEntryKind.AnimEntry`) all 5 fields as required, non-optional properties, so the far more common case gets full type safety and callers narrow on `entry.kind` exactly like they already narrow on `CommonTokenKind`.

This also means `parseAnimationCfg` does **not** reproduce the original engine's own behavior here. Tracing `BG_ParseAnimationFile`: its field-2-through-5 `if (!token) break;` checks are dead code (`COM_ParseExt` never returns a null *pointer*, only an empty string), so the real engine actually keeps looping and silently assigns `atoi("") == 0` (and `fps`'s own `0 → 1` default) to every remaining field of the *same* record before finally breaking on the *next* record's empty-name check. This codebase surfaces an explicit `IncompleteAnimEntry` + `AnimEntryWarning.IncompleteEntry` instead of silently fabricating zeros for the missing fields — more useful for a caller (and matches the parent issue's own framing: flagged, not silently completed).

## No synthetic terminal marker at this layer

`tokenize()` always yields a trailing `Eof` token so callers get an explicit signal rather than inferring "no more tokens" from the generator simply stopping (see `decisions/common-tokenizer.md`). `parseAnimationCfg` deliberately does **not** do the analogous thing — it just returns like any other generator in this codebase (e.g. `iterSurfaces()` in `src/glm.ts`), with no synthetic terminal `AnimEntry`-ish marker. The reason `commonTokenizer` needed an explicit `Eof` was specifically to disambiguate true end-of-input from an embedded NUL at the *byte* level, for diagnostics that only make sense there; that ambiguity doesn't need duplicating at the entry level. It's still fully recoverable by running `tokenize()` directly, and the one place it's actually relevant here — a record cut short mid-entry — is already carried on `IncompleteAnimEntry.eofReason`.

## Hand-rolled `integer`/`number` parsing, not `parseInt`/`parseFloat`

`parseAnimInteger`/`parseAnimNumber` must not delegate to JS's built-ins, because those diverge from `atoi`/`atof` (and from the grammar's own `integer`/`number` rules) in ways worth avoiding rather than silently reproducing or silently "fixing":

- `parseInt("0x1F")` auto-detects a hex prefix and returns `31`; `atoi("0x1F")` (and the grammar's `integer = ["-"] 1*DIGIT`) stops at `x`, giving `0`.
- `parseFloat("5e10")` interprets scientific notation and returns `5e10`; the grammar's `number` rule has no exponent alternative, so per "leading digit run wins, trailing junk ignored" only `5` is recognized, giving `5`.
- `parseFloat("Infinity")` / `parseFloat("NaN")` recognize those literals; `atof` and the grammar's `number` rule do not.

Both functions instead extract the leading match with a regex mirroring the ABNF exactly (`/^-?[0-9]+/` for `integer`, `/^-?(?:[0-9]+(?:\.[0-9]*)?|\.[0-9]+)/` for `number`, applied to `tokenValue(source, token)`, which already dequotes) and then convert *only* that matched substring digit-by-digit by hand, rather than handing the matched text to `parseInt`/`parseFloat` — even though the match is already vetted to contain nothing exotic, the point of "hand-rolled" is that no path in this module ever calls either built-in. No match at all (e.g. `"walk"`, an empty field) yields `0`, mirroring `atoi`/`atof`'s "no conversion performed" behavior.

One deliberate, documented divergence from a strict reading of `atoi`/`atof`: both accept an optional leading `+` (and leading whitespace, moot here since tokens never start with whitespace). The grammar's `integer`/`number` rules (`["-"] 1*DIGIT`) don't provide for a leading `+`, so a token literally starting with `+` (e.g. `+5`) parses as `0` here, not `5` — matching the grammar, not strict `atoi`/`atof`, since the issue asked for grammar-conformant parsing.

No warning is raised for trailing junk being ignored (`"5foo"` → `5`) or no leading digit at all (`"walk"` → `0`) — both mirror the original engine's own silent behavior, and nothing asked for a "field doesn't look numeric" diagnostic. That's a plausible future addition (useful for the eventual language-server story) but is intentionally not part of `AnimEntryWarning`, which stays closed to exactly what this parser actually needs to flag today.

## Fields store the raw `AnimFieldToken`, not a derived value — and why that's not the same "no `text` field" rule

`decisions/common-tokenizer.md`'s "no `text` field" rule is about not storing something *trivially* re-derivable from a token's own `start`/`end` (a plain source slice). Parsing `first-frame`'s numeric value isn't a trivial slice — it's real leading-digit-run extraction — so it doesn't fall under that rule the same way. `AnimEntry` still doesn't cache the parsed number, for a different reason: keeping only the token, with `parseAnimInteger`/`parseAnimNumber` as separate pure functions of `(source, token)` (mirroring `tokenValue`'s own shape), keeps `AnimEntry` a pure structural/span record, and lets a caller who only wants `entry.name`'s text call `tokenValue()` without also paying for eagerly-parsed numbers it may not need.

This also resolves — by not needing — the "deferred generalization" `TokenBase`'s own doc comment in `src/token.ts` calls out: a future aggregate token type wanting each warning to carry its own span. Because each field on `AnimEntry` **is** the real underlying `CommonToken`, a consumer that wants to know whether the `fps` field itself carries e.g. `TokenTooLong` just reads `entry.fps.warnings` directly — no change to `TokenBase`/`Token` needed, and `AnimEntry`'s own top-level `warnings` stays reserved for anomalies belonging to the *entry as a whole* (currently only `IncompleteEntry`).

## `tokens`: every token consumed while collecting an entry, so no warning is lost

Both `AnimEntry` and `IncompleteAnimEntry` also carry `tokens: readonly CommonToken[]` — every token `parseAnimationCfg` passed over while collecting that entry, in order, including the `Whitespace`/`LineComment`/`BlockComment` tokens skipped between the 5 named fields, not just the named fields themselves. This was added after the initial plan (which had originally scoped "surfacing anomalies from skipped separator tokens" as out of scope) specifically because a separator between two fields can itself carry a warning — e.g. an `UnterminatedBlockComment` on a block comment that swallows the rest of the record — and without `tokens`, that warning would be silently unreachable from an `AnimEntry`/`IncompleteAnimEntry` alone: a caller would have to separately re-run `tokenize()` and re-derive the same entry boundaries just to notice it.

With `tokens` present, `entry.tokens.flatMap(t => t.warnings)` always recovers every warning produced while parsing that entry, without a second tokenization pass. Implementation-wise, `parseAnimationCfg`'s field-pulling helper (`pull()`) appends every token it passes over — skipped separators and the real token it returns — to a per-entry accumulator, which is attached as `tokens` when the entry (complete or incomplete) is yielded, then reset for the next one. The accumulator always includes any separator immediately preceding the entry's own `name` token too (it's collected while searching for `name`, after the previous entry's own `tokens` was already yielded and reset) — so concatenating every yielded entry's `tokens` in order reconstructs the full `tokenize()` stream exactly, up to (and, only for a trailing `IncompleteAnimEntry`, including) the terminal `Eof` token.

## Empty quoted `anim-name` (`""`) mid-file: a deliberate non-reproduction of an engine quirk

In the original engine, an empty quoted `anim-name` is a genuinely surprising case: `COM_ParseExt` returns `com_token[0] == 0` for an empty quoted string the same as for true EOF, so `BG_ParseAnimationFile`'s `if (!token || !token[0]) break;` check means a literal empty quoted anim-name (`""`) silently truncates the rest of the file in the real engine, even if valid entries follow it. This codebase does not reproduce that: `commonTokenizer` reports `""` as an ordinary, non-`Eof` `QuotedToken`, so `parseAnimationCfg` treats it as a normal (if useless) `anim-name` and keeps parsing subsequent entries normally. This matches the grammar's own stated scope (an unrecognized/unusual name has no bearing on syntax) and is covered by a test case (`src/animationCfg.test.ts`) asserting that entries after an empty-quoted-name entry still parse.
